## 1. مراجعة الفكرة الحالية

### اللي المشروع بيعمله فعلًا

```
  المستخدم                    الذكاء الاصطناعي              المحرك الحتمي (Deterministic)
 ┌──────────────┐         ┌──────────────────────┐      ┌──────────────────────────────┐
 │ مساحة + نوع  │         │  استدعاء واحد بس:     │      │ بحث نِسَب القطعة              │
 │ + وصف حر     │  ────▶  │  brief →              │ ──▶  │ توزيع الشرايط والبلاطات      │
 │              │         │  ArchitecturalProgram │      │ الأبواب والشبابيك والمناور    │
 └──────────────┘         │  (غرف + مساحات +      │      │ المراجعة الكودية              │
                          │   علاقات + ملاحظات)   │      │ الرسم SVG/PDF/DXF/3D          │
                          └──────────────────────┘      │ تركيب أدوار المبنى            │
                                                        └──────────────────────────────┘
```

**النقطة الأهم في التشخيص:** الذكاء الاصطناعي في المشروع دلوقتي = **استدعاء واحد**
(`planner/ai.py:build_program`). كل حاجة تانية — الهندسة، الرسم، المراجعة، التقرير،
المجسّم، تركيب المبنى — حتمية بالكامل.

### الأصل الحقيقي للمشروع (ودي نقطة الانطلاق لكل اقتراح تحت)

الأصل مش إن المشروع "بيستخدم AI". الأصل إن عنده **مُتحقِّق موثوق**:

- `engine/validate.py` — بيحكم على أي مخطط بأرقام: أقل بُعد، أقل مساحة، نِسَب
  الإضاءة، وجود باب لكل فراغ، عرض الفتحات.
- `engine/layout.py` — بيضمن *رياضيًا* إن الفراغات بتغطي القطعة من غير تداخل ولا
  مساحة ضايعة، وإن كل فراغ لامس مسار الحركة.
- `knowledge.py` — 20 معيار فراغ + معايير المبنى والمناور، كلها أرقام مكتوبة صراحة.

ده بالظبط اللي الـ LLM **مش** بيعرف يعمله. فأي ميزة AI جديدة قيمتها الحقيقية
بتيجي من إنها **تستغل المُتحقِّق ده كإشارة حكم**، مش من إنها تطلب من الموديل يرسم أكتر.

كل الأفكار تحت مترتّبة على المبدأ ده. والأفكار اللي بتخالفه (زي توليد رندر بالـ AI)
معلّم عليها صراحةً إنها استعراضية.

## 2. الاقتراحات كاملة

### مجموعة (أ) — إغلاق الحلقة بين الـ AI والمُتحقِّق

هي أقوى مجموعة، لأن البنية التحتية بتاعتها **موجودة أصلًا**.

---

#### أ-1 · حلقة الإصلاح الذاتي — Self-Repair Loop

| | |
|---|---|
| **المشكلة** | الموديل بيكتب البرنامج وهو أعمى. لو الناتج فيه 12 مخالفة، محدش بيقوله. حاليًا `_trim_program` بيحاول يصلّح بطريقة غبية: بيشيل غرف بالأولوية. |
| **الصعوبة** | **سهل → متوسط** |
| **الأولوية** | **Must Have** |
| **الأثر** | تقليل مباشر في المخالفات المقاسة (حالة المكتب 350 م² عندها 60 مخالفة دلوقتي) |

**خطوات العمل داخل المشروع:**

1. بعد `solve()` في `service.py:solve_with_trimming`، لو `layout.metrics["errors"] > 0`:
2. نبني رسالة فيها: البرنامج الحالي + أبعاد القطعة الفعلية + **قائمة المخالفات
   بالنص الكامل** + المخطط الناتج مبسّط (اسم الفراغ وأبعاده).
3. نطلب من الموديل **برنامج معدّل** مستهدف المخالفات دي بالتحديد، بنفس الـ schema.
4. نعيد `solve()`، ونقارن `issue_penalty` القديم بالجديد، ونمسك الأحسن.
5. حد أقصى 2–3 لفّات، مع سقف زمني. لو مفيش تحسّن نوقف ونبلّغ.

**التقنيات:** LLM بـ structured output + `validate()` كإشارة حكم.
دي فعليًا **agent بحلقة verifier** — من غير framework، بالكود الموجود.

**المتطلبات:** لا شيء جديد. نقطة الربط `service.py:117`.

---

#### أ-2 · الحوار التصميمي — Conversational Design Loop

| | |
|---|---|
| **المشكلة** | الأداة توليد لمرة واحدة. «الماستر صغير، كبّره على حساب السفرة» = ابدأ من الأول واخسر كل حاجة. ودي أكبر فجوة في تجربة المستخدم كلها. |
| **الصعوبة** | **متوسط** |
| **الأولوية** | **Must Have** |
| **الأثر** | بتحوّل الأداة من *مولّد* لـ *شريك تصميم*. أكبر قفزة ممكنة في التجربة. |

**خطوات العمل:**

1. نموذج جديد `ProgramEdit{op, room_id, field, value, reason}` — الموديل بيرجّع
   **تعديل** مش برنامج جديد. ده حاسم: بيحافظ على باقي التصميم ثابت.
2. `SessionStore` (in-memory أول الأمر، SQLite بعدين) بيحفظ:
   البرنامج الحالي + آخر `Layout` + سجل التعديلات.
3. `POST /api/chat` بياخد `{session_id, message}` ويرجّع
   `{edits[], new_svg, diff_summary, before_after_metrics}`.
4. نطبّق التعديلات، نعيد الحل، ونعرض **قبل/بعد** جنب بعض مع فرق الأرقام.
5. **Undo stack** — أي تعديل قابل للتراجع.
6. في الواجهة: شريط محادثة تحت المخطط، وكل رد فيه زر «طبّق» و«تراجع».

**التقنيات:** LLM + tool use / structured output، إدارة جلسات، streaming للرد.

**المتطلبات:** تخزين جلسات، وتعديل في `app.js` و`api.py`. مفيش API خارجي.

---

#### أ-3 · المراجع الكودي الذكي — Explainable Code Review

| | |
|---|---|
| **المشكلة** | `validate()` بيقول «أقل بُعد 1.51 م أقل من 1.55 م». صح، بس مش قابل للتنفيذ. المستخدم مش عارف يعمل إيه. |
| **الصعوبة** | **سهل → متوسط** |
| **الأولوية** | **Must Have** |
| **الأثر** | بتحوّل قايمة مخالفات مُحبِطة لقايمة مهام واضحة |

**خطوات العمل:**

1. نبعت للموديل: `issues[]` + هندسة المخطط + البرنامج.
2. الموديل يرجّع لكل مخالفة: **السبب الجذري** + **2–3 حلول عملية بالأرقام**
   («كبّر عرض الشريط 6 سم على حساب الصالة» / «شيل حمام الماستر واعمله مشترك»).
3. كل حل يرجع كـ `ProgramEdit` قابل للتطبيق بضغطة (بيتكامل مع أ-2).
4. نعرضه في تبويب «المراجعة» الموجود أصلًا.

**التقنيات:** LLM + structured output. (RAG اختياري لو الكود اتعمله فهرسة — بند ج-1.)

#### أ-4 · البدائل بالنيّة — Intent-Driven Alternatives

| | |
|---|---|
| **المشكلة** | `--alternatives 2` بيدّي نفس البرنامج بترتيب هندسي مختلف. مش بدائل تصميمية. العميل عايز 3 *أفكار*. |
| **الصعوبة** | **متوسط** |
| **الأولوية** | **Must Have** |
| **الأثر** | بتحوّل المخرج من «مخطط» لـ «قرار بين خيارات مفهومة» |

**خطوات العمل:**

1. نطلب من الموديل K برامج تحت **أطروحات تصميمية مختلفة صراحةً**:
   «أوفر مساحة معيشة» · «خصوصية أعلى للمنطقة الليلية» · «أقل تكلفة سباكة».
2. نحل كل واحد بالمحرك (متوازي).
3. استدعاء تركيبي أخير: جدول مقارنة بالأرقام الحقيقية من `metrics`
   + سطرين لكل بديل: مكسبه إيه وثمنه إيه.
4. نعرضهم كـ 3 خيارات **بأسماء ومبررات**، مش «بديل 1، بديل 2».

**التقنيات:** استدعاءات متوازية + المحرك الحالي + استدعاء تلخيص.

#### ج-1 · الكود كقاعدة معرفة — Code-as-RAG

| | |

### مجموعة (د) — مخرجات جديدة (أبعد من المخطط)

---

#### د-1 · الكميات والتكلفة — AI Quantity Take-off & Cost

| | |
|---|---|
| **المشكلة** | أول سؤال بيسأله أي عميل: «هيتكلف كام؟». المخطط لوحده مالوش إجابة. |
| **الصعوبة** | **متوسط** |
| **الأولوية** | **Must Have** |
| **الأثر** | **أكبر مضاعِف قيمة في الوثيقة** — والجزء الصعب منه محسوب أصلًا |

**ليه سهل أكتر مما يبدو:** الهندسة عندنا **دقيقة**. `metrics["wall_length"]` موجود.
أطوال الحوائط وسُمكها، ومساحات الفراغات، وعدد الأبواب والشبابيك وأبعادها — كلها
أرقام مضبوطة في `Layout`. حساب الكميات **حتمي بالكامل، من غير AI**.

**خطوات العمل:**

1. **حتمي:** من `Layout` نحسب — م³ مباني، م² محارة، م² بلاط، عدد ووحدات الأبواب
   والشبابيك، أطوال السباكة من تجميع الفراغات الرطبة، نقاط الكهرباء بقاعدة لكل فراغ.
2. **AI:** تصنيف البنود لمسمّيات السوق المحلي، وكتابة السرد والافتراضات.
3. **الأسعار من مصدر بيانات (ملف أسعار أو API) — مش من ذاكرة الموديل.**
   سعر مهلوس أسوأ من مفيش سعر خالص.

## 4. أفضل 10 — وليه بالتحديد

### 1. حلقة الإصلاح الذاتي (أ-1)
**الفايدة:** بتقلّل المخالفات في المخططات الفعلية — أرقام تقدر تقيسها قبل وبعد.
**ليه اتختارت أولًا:** أعلى نسبة عائد/تكلفة في الوثيقة كلها. المُتحقِّق
(`validate()`) موجود وموثوق، ونقطة الربط (`solve_with_trimming`) موجودة. إنت
عندك آلة حكم شغّالة والموديل مش شايفها — ده هدر واضح. حالة المكتب 350 م² بـ60
مخالفة دي بالظبط اللي المفروض تتحسّن.

### 2. الحوار التصميمي (أ-2)
**الفايدة:** المستخدم يقدر يقول «كبّر الماستر على حساب السفرة» ويشوف النتيجة فورًا.
**ليه:** هي **الجزء الكامل الناقص** من النظام. التصميم عملية تكرارية بطبيعتها،
والأداة دلوقتي بتوليد مرة وتقف. ودي كمان اللي بتخلّي الأفكار 4 و7 و8 قابلة
للاستخدام فعلًا — كلها بتحتاج مكان يتطبّق فيه اقتراح.

### 3. الكميات والتكلفة (د-1)
**الفايدة:** جواب على أول سؤال بيسأله أي عميل.
**ليه:** أكبر مضاعِف قيمة، والجزء الصعب منه (الهندسة الدقيقة) **محسوب أصلًا** —
`wall_length` والمساحات وعدد الفتحات كلها موجودة في `Layout`. الحساب حتمي 100%
والـ AI دوره تصنيف وسرد بس. شرط واحد: الأسعار من مصدر بيانات مش من ذاكرة الموديل.

### 4. المراجع الكودي الذكي (أ-3)
**الفايدة:** «أقل بُعد 1.51 م» تتحوّل لـ«كبّر الشريط 6 سم على حساب الصالة».
**ليه:** المخالفات موجودة ومكتوبة كويس، بس مالهاش طريق للحل. التنفيذ رخيص،
والأثر مباشر على الإحباط. وبيتكامل مع أ-2 (كل اقتراح زر «طبّق»).

### 5. مجموعة التقييم الآلية (و-1)
**الفايدة:** تعرف إن تعديلك حسّن ولا وحّش، برقم.
**ليه اتختارت رغم إنها مش ميزة للمستخدم:** من غيرها، كل تحسين في البرومبت بعد
كده تخمين. عندك 190 اختبار بيقيسوا **الصحة**، وصفر اختبار بيقيس **الجودة**. دي
الميزة اللي بتخلّي التسعة التانيين آمنين. ودي كمان الحاجة اللي بتفرّق مشروع
هندسي عن ديمو.

### 6. وكيل الجدوى العقارية (هـ-1)
**الفايدة:** «عندي 500 م² — أعمل فيها إيه؟» بدل «ارسملي 4 شقق».
**ليه:** بيعيد تعريف المنتج من أداة رسم لأداة قرار — وده أعلى تمييز تنافسي.
والجزء الصعب (تركيب المبنى كامل بالمناور والنواة والمراجعة) **اتعمل خلاص**.
اللي ناقص طبقة تنسيق فوقه بس.

### 7. البدائل بالنيّة (أ-4)
**الفايدة:** 3 أفكار بأسماء ومبررات بدل 3 ترتيبات هندسية.
**ليه:** خانة `alternatives` موجودة ومتوصّلة بالواجهة والـ API — التغيير في
المحتوى مش في البنية. والعميل بيتعامل مع «خصوصية أعلى للنوم» أحسن بكتير من
«بديل 2».

### 8. التحليل الشمسي والتوجيه (د-2)
**الفايدة:** المخطط يراعي الشمس، مش بس الكود.
**ليه:** `north_angle` موجود في النموذج ومستخدم **في رسم سهم الشمال وبس**. حقل
ميّت. وفي مناخ زي مصر، التوجيه من أهم قرارات التصميم. والأهم إنه يتحط كعقوبة في
`_score_room` — يعني المحرك **يصمّم أحسن**، مش بس يعلّق. الفيزياء نفسها حتمية،
فمفيش خطر هلوسة.

### 9. من الاسكتش للمخطط (ب-1)
**الفايدة:** تصوّر رسمة إيد وتطلع مخطط بالمقاسات.
**ليه:** أعلى تمييز تنافسي بين مداخل البيانات، ومناسب لطريقة تفكير المعماريين
فعلًا. اتحطّت تاسعة مش أولى لأنها بتضيف سطح فشل جديد (رفع صور، دقة الرؤية) —
فالأفضل تيجي بعد ما حلقة التصميم الأساسية تستقر. **شرط:** شاشة تأكيد، من غير ثقة صامتة.

### 10. سجل القرارات (و-2)
**الفايدة:** المشروع بيشرح نفسه — ليه النسبة دي، ليه المدخل ده، إيه اللي اتشال وليه.
**ليه:** أرخص بند في القايمة وأعلى عائد مصداقية. وبيخدم مباشرة سيناريو المناقشة
الأكاديمية. ومفيش فيه أي خطر تقني — تسجيل قرارات موجودة أصلًا.

```
  المرحلة 1: الفهم        المرحلة 2: الحوار         المرحلة 3: القرار
 ┌────────────────┐      ┌──────────────────┐      ┌─────────────────────┐
 │ نص · صوت       │      │ توليد            │      │ 3 بدائل بمبررات      │
 │ اسكتش · كروكي  │ ───▶ │ ↕ إصلاح ذاتي     │ ───▶ │ + كميات وتكلفة       │
 │ (ب-1، ب-2، ب-3)│      │ ↕ تعديل بالحوار  │      │ + تحليل شمسي        │
 └────────────────┘      │ (أ-1، أ-2، أ-3)  │      │ + جدوى (هـ-1)       │
                         └──────────────────┘      └─────────────────────┘
                                  │                          │
                                  └──── سجل القرارات (و-2) ───┘
```

**إزاي بيتكامل مع الموجود:** كل المراحل دي **بتلبس فوق** المحرك الحالي من غير
ما تلمسه. `engine/` و`drafting/` و`knowledge.py` تفضل زي ما هي بالظبط — وهي
أثمن حاجة في المشروع. اللي بيتغيّر: `api.py` (جلسات + مسارات جديدة)،
`service.py` (حلقة الإصلاح)، والواجهة (شريط حوار + تبويبات جديدة).

**التغيير التقني الوحيد المطلوب فعلًا:** إدخال **حالة الجلسة** (session state).
دلوقتي `POST /api/design` بلا ذاكرة. أول ما تدخل الجلسة، الحوار والتعديل
والتراجع والمقارنة كلهم بيبقوا ممكنين.
